# PostgreSQL CDC preparation

This directory records the offline contracts for a later independent Debezium Server deployment. The product design uses PostgreSQL physical replication for standby copies, the existing Egon MP-SDJ native rules for application read/write routing, and a PRIMARY-only logical slot feeding Debezium Server and RabbitMQ. Those are three distinct paths. No Kafka broker, Canal process, Outbox table, search engine, Kubernetes manifest, or Egon component change is part of this preparation.

The raw route contains committed PostgreSQL facts. Goods validates a source registry, computes stable per-tenant advertisement invalidations and product refresh requests, and publishes them with persistent AMQP messages. It acknowledges a raw message only after all resulting semantic publishes receive confirmations with no return. The advertisement listener validates the current source epoch and trusted tenant scope, attempts the existing cache invalidation SPI, restores thread context, and ACKs the attempt. The product refresh queue has no consumer in this phase; a later search owner must reread current state from PRIMARY and implement deduplication, fencing, and tombstones before acknowledging work.

Application CDC stays disabled in every profile. Enabling `app.cdc.enabled` requires an explicit `master_data` registry with the approved source name, epoch, topic prefix, database, `public` schema, and exactly the `ad`, `spu`, and `sku` tables. It also requires the `spring.rabbitmq` correlated confirm and return configuration and the already-reviewed Rabbit topology. The original sample Rabbit integration retains its existing profile values and routes. The Server's `source.name` and topic prefix must match the application registry for the same epoch.

Use `debezium/application.properties` as a property-name/config-shape template. Required PG credentials, host, source name, slot, publication, offset-file path, Rabbit credentials, vhost, and TLS material are deployment inputs; no secrets belong in Git. Before enabling a source, pin the official Debezium Server distribution, PostgreSQL connector and AMQP sink modules, and an immutable `sha256` image digest. Verify the exact Rabbit virtual-host/TLS pass-through keys against that release. The template was checked against the [Debezium Server 3.2 reference](https://debezium.io/documentation/reference/3.2/operations/debezium-server.html) and [PostgreSQL connector 3.2 reference](https://debezium.io/documentation/reference/3.2/connectors/postgresql.html); this does not select a production release.

| Environment input | Use |
| --- | --- |
| `CDC_SOURCE_NAME` | Debezium `topic.prefix` and the registered source name |
| `CDC_SOURCE_EPOCH` | Current goods `app.cdc.source-registry.master_data.source-epoch`; change only through the approved discontinuity/rebuild procedure |
| `CDC_DATABASE`, `CDC_PUBLICATION_NAME`, `CDC_SLOT_NAME` | Exact database/publication/slot for the one PRIMARY source |
| `CDC_PG_PRIMARY_HOST`, `CDC_PG_PRIMARY_PORT`, `CDC_PG_REPLICATION_USER`, `CDC_PG_REPLICATION_PASSWORD`, `CDC_PG_SSLMODE`, `CDC_PG_SSLROOTCERT` | PRIMARY replication connection; secrets and certificates are supplied outside Git |
| `CDC_RABBIT_HOST`, `CDC_RABBIT_PORT`, `CDC_RABBIT_USER`, `CDC_RABBIT_PASSWORD`, `CDC_RABBIT_VHOST`, `CDC_RABBIT_CONFIRM_TIMEOUT_MS` | Rabbit connection and bounded confirm budget; map vhost/TLS with the exact pinned sink artifact |
| `CDC_OFFSET_FILE` | File under the persistent single-writer offset volume |

The PostgreSQL owner supplies PRIMARY/standby topology, role grants, publication, `REPLICA IDENTITY FULL`, RPO, WAL budget, slot ownership, fencing and recovery evidence. The RabbitMQ owner pre-creates the documented bindings and policies, grants Debezium access only to the raw exchange, and verifies durable quorum/alternate-exchange/dead-letter behavior. Kubernetes must run one active source owner with a persistent offset volume. The Kubernetes owner supplies namespace, domain, storage class, single-writer PVC, resource budgets, termination grace, and NetworkPolicy rules from the Server to PostgreSQL PRIMARY and RabbitMQ, and from goods to its existing PostgreSQL/Redis/RabbitMQ dependencies. A readiness probe or lease does not fence an old source owner.

The existing goods and Envoy deployment files remain the source of truth for that application. This directory adds no deployable manifest and does not change existing gateway routes, BFF behavior, upload limits, or CORS configuration. Before exposing anonymous homepage reads, the platform owner must separately register the approved hostname→tenant mapping and the exact Yuheng gateway route with `AuthenticationMode.NONE`; management permission grants remain an independent USER/RBAC setup.

Run `bash scripts/work/2026-10-10-16-13-postgresql-cdc-advertisement-implementation-verify.sh --self-test` for the current offline verifier. `--deployment` validates the static configuration and documentation contracts and reports the live release gate as blocked until TEST-019–022 are recorded in [acceptance.md](acceptance.md). These commands do not start, install, or connect to PostgreSQL, RabbitMQ, Redis, Debezium Server, or Kubernetes.
